# Working on this repository

Read ARCHITECTURE.md first. These are the standards every change follows.

## UI standards
- **Mobile first** with Tailwind: unprefixed classes are the phone layout; add `sm:`/`md:`/`lg:` for larger screens. No sideways page scroll at 360px; tap targets of at least 44px.
- **Theme tokens only** (`bg-surface`, `text-muted`, `border-line`, `bg-accent`…) from `src/styles.css`; green accent; light and dark mode.
- **Every section is collapsible.** Wrap each titled section below the page heading, and each titled part of a side panel, in `<Section id="page.part" title="…">` from `src/components/Section.tsx` (`level="h4"` in panels; optional `summary`). Never use a bare `<h2>` section. The page heading (h1) is not collapsible.
- **One pinned action button.** Mark a section's main action button with `data-pin` and an open form's Save with `data-pin="2"`; `PinnedAction` (in `App.tsx`) pins one of them under the header: an Add once it scrolls past the top; an open form's Save always, for as long as the form is open (disabled until there's something to save), wherever the form is on the page. This works the same on every page. Sections (`Section`) and side panels (`<aside data-pin-scope>`) are the scopes.
- **Forms wait for Save; tables save as you go.** In a form or side panel every field (picks included) is held until Save, with Undo changes beside it and an "Unsaved changes" hint; register the form with `useUnsaved(changed)` from `src/lib/unsaved.ts` so switching rows or leaving the page asks first (`confirmDiscard()` before changing the selected row). A table cell saves as soon as its edit ends. Actions such as adding a sub-task or a note, or ticking a sub-task done, happen at once.
- **Adding opens the new item's form.** After an add succeeds, select the new item, open its form or side panel, highlight its row (`reveal={{ id, n: Date.now() }}` on `LatticeGrid`) and bring the form into view (`scrollToForm(id)` from `src/lib/reveal.ts`, with `data-form-for={id}` on the panel). Anything created on its own page (company, project) opens there with its details form (`navigate(path, { state: { created: true } })`). Call `confirmDiscard()` before adding, since the selection moves.
- **Forms open under their table.** A row's form or side panel goes below its grid (or calendar) on every screen size, so the table keeps the full width; lay a wide panel's fields out in two columns from `md:`/`lg:` up. A project's areas are separate pages with a left nav (`src/pages/project/ProjectLayout.tsx`); a new area is a nested route there plus an entry in its nav.
- **Tables use lattice-grid** through `src/components/LatticeGrid.tsx`. Columns edited by picking from a list use `editor: 'select'` and render with `gridDropdown` (caret; the wrapper opens it on one click and saves on pick, and gives the column a dropdown filter of its values); see `TaskTree.tsx`. On phones (under 640px) the wrapper unpins every column, including the tree/group and tick-box columns, so whole rows scroll sideways together; don't re-pin them for phones.
- **Dropdown filters for fixed values.** Any column whose values come from a fixed set (pick-lists, statuses, departments, yes/no, "You are") filters with a dropdown of tick boxes and counts (`filter: 'set'`; pick-list columns get it automatically from the wrapper). Columns holding a list of names (roles, tags) add `filterSplit: ','` so each name is its own choice. Free text, dates and numbers keep the typed filter.
- **Every field is editable in both the table and the form.** Anything a person may change is editable in place in its table and in the page's form or side panel; adding a field means adding it to both. Lists of names (roles, tags) are comma-separated in the table and picked in the panel. If a row's name is editable, give the link its own Open column. Fields owned by another record stay read-only outside their home: a person's name, nickname and phone are edited on the company's People list (by admins) or the person's profile, and the sign-in email only by the person on their profile.
- **People without accounts.** A profile can exist before its person signs up (`profiles.has_account = false`); it's claimed on sign-up by email. Anything that links to a person references `profiles(id)` with `on update cascade` (and so do links to `company_members` / `project_members`). Show `InviteButtons` wherever an admin sees a person without an account.
- **Phones and emails** use `src/lib/contact.ts`: `phoneOrThrow`/`formatPhone` (stored as ###-###-####, or + and digits) and `emailOrThrow`/`emailProblem`; any new phone or email field uses them and the database's `format_phone`/`check_email`.

## Data and API
- The app reads and writes data only through the API client in `src/lib/api.ts`.
- API routes live in `supabase/functions/api/routes/`, with zod schemas in `schemas.ts`; run `npm run api:spec` after changing them.
- Database changes are a new numbered file in `supabase/migrations` (never edit an applied one), with tests in `tests/schema.test.mjs`. Security rules live in the database (row-level security).

## Checks
`npm run typecheck`, `npm run test:db`, `npm run build`.
