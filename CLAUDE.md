# Working on this repository

Read ARCHITECTURE.md first. These are the standards every change follows.

## UI standards
- **Mobile first** with Tailwind: unprefixed classes are the phone layout; add `sm:`/`md:`/`lg:` for larger screens. No sideways page scroll at 360px; tap targets of at least 44px.
- **Fields never overlap, at any width.** Every input, select and textarea uses `.field` (date and time pickers included: `.field` drops Safari's fixed-width native box so they fit their column on iPad and iPhone). Side-by-side layouts use `minmax(0, 1fr)` grid columns or `min-w-0` flex items so long content wraps instead of pushing past its box. Check new forms at 360px, iPad portrait (768–820px), iPad landscape (1024–1180px) and desktop.
- **Theme tokens only** (`bg-surface`, `text-muted`, `border-line`, `bg-accent`…) from `src/styles.css`; green accent; light and dark mode. Boxes people type in or pick from use `border-field-line` (3:1 contrast, built into `.field`); `border-line` is for dividers and cards.
- **Every section is collapsible.** Wrap each titled section below the page heading, and each titled part of a side panel, in `<Section id="page.part" title="…">` from `src/components/Section.tsx` (`level="h4"` in panels; optional `summary`). Never use a bare `<h2>` section. The page heading (h1) is not collapsible.
- **One pinned action button.** Mark a section's main action button with `data-pin` and an open form's Save with `data-pin="2"`; `PinnedAction` (in `App.tsx`) pins one of them under the header: an Add once it scrolls past the top; an open form's Save always, for as long as the form is open (disabled until there's something to save), wherever the form is on the page (reading "No changes" while disabled, and with "<the form's data-form-label> ↓" beside it while the form is off screen). This works the same on every page. Sections (`Section`) and side panels (`<aside data-pin-scope>`) are the scopes.
- **Forms wait for Save; tables save as you go.** In a form or side panel every field (picks included) is held until Save, with Undo changes beside it and an "Unsaved changes" hint; register the form with `useUnsaved(changed)` from `src/lib/unsaved.ts` so switching rows or leaving the page asks first (`confirmDiscard()` before changing the selected row). A table cell saves as soon as its edit ends. Actions such as adding a sub-task or a note, or ticking a sub-task done, happen at once.
- **Adding opens the new item's form.** After an add succeeds, select the new item, open its form or side panel, highlight its row (`reveal={{ id, n: Date.now() }}` on `LatticeGrid`) and bring the form into view (`scrollToForm(id)` from `src/lib/reveal.ts`, with `data-form-for={id}` on the panel). Anything created on its own page (company, project) opens there with its details form (`navigate(path, { state: { created: true } })`). Call `confirmDiscard()` before adding, since the selection moves.
- **Items link to their home page.** An item shown anywhere other than its own page (a scene on a shoot day or call sheet, a location on a task, a person on a call sheet, a task's category, a task on the Overview) links to its home page, which opens with the item selected, highlighted and its form open. Build the path with `itemPath` from `src/lib/links.ts` (`?open=<id>`), and make every home page read it with `useOpenFromLink` from `src/lib/reveal.ts` (a new kind of item gets an `itemPath` entry and the hook on its page). In tables, read-only cells use `gridLinkHtml`/`gridLinkList`; pick-list cells pass `{ to, title }` as `gridDropdown`'s second argument for a small open arrow (a click elsewhere still opens the list). In forms, put an `OpenLink` under the picker for what's picked. Leave the public call sheet pages (personal `/sheet/<token>` and shared `/call-sheet/<token>`) as plain text.
- **"Back to …" after every item link.** Following an item link shows "‹ Back to <where you were>" at the top of the page it opens (and in the pinned bar once scrolled), and going back reopens the form that was open; see `src/lib/backLink.ts`. It works for every item link automatically. A home page's item form carries `data-form-for={id}` and `data-form-label="<its name>"` (e.g. `Scene 3`), so the link says where it goes back to; a page with no item form can set `data-page-label`. Use `itemPath` links (or `gridLinkHtml`/`OpenLink`) so links are recognised; don't build navigation that bypasses them.
- **Forms open under their table.** A row's form or side panel goes below its grid (or calendar) on every screen size, so the table keeps the full width, and the page scrolls down to it when it opens (`FormScroller` in `App.tsx` does this for any new `[data-form-for]`, after any cell edit or pick list in progress closes); lay a wide panel's fields out in two columns from `md:`/`lg:` up. A project's areas are separate pages with a left nav (`src/pages/project/ProjectLayout.tsx`); a new area is a nested route there plus an entry in its nav.
- **Tables use lattice-grid** through `src/components/LatticeGrid.tsx`. Columns edited by picking from a list use `editor: 'select'` and render with `gridDropdown` (caret; the wrapper opens it on one click and saves on pick, and gives the column a dropdown filter of its values); see `TaskTree.tsx`. On phones (under 640px) the wrapper unpins every column, including the tree/group and tick-box columns, so whole rows scroll sideways together; don't re-pin them for phones. Give every table a unique `stateId` (e.g. `"company.people"`): it names the table for the Columns button, and the person's view of it (columns shown, widths, order, sort) is kept for the browser session.
- **Touch-sized tables.** On touch screens (`pointer: coarse`: iPad, phones) the `LatticeGrid` wrapper makes rows and header rows 44px, and `styles.css` gives filter boxes, editors and tick boxes tap sizes and 16px text (so Safari doesn't zoom). Size a table with `gridHeight(chrome, rows, max)` from `LatticeGrid.tsx`, never `rows * 34`. Date columns show `Mar 12, 2027` (`tableDate`); write dates in text with the helpers in `src/lib/format.ts` (`shortDate`, `longDate`, `dateRange`), never as raw `2026-12-07`.
- **One help line above each table.** Use `TableHint` (`src/components/TableHint.tsx`): one short sentence above the table, the rest in `more` behind "More tips". Say "Tap" and "Double-tap (or double-click)", since the app is used on an iPad. Add forms with more than one box give each box a visible label (`<label className="label">`), not just a placeholder.
- **Paging only where data keeps growing.** Tables don't page: they load all their rows and scroll. Only a table that keeps growing without limit (the activity log and Project notes) pages, and it's paged by the server: the API takes `offset`/`limit`, filters, `q` and the order and returns `total`; the page uses `useServerPages` (`src/lib/serverPages.ts`) and passes `paging` to `LatticeGrid`, gives set filters their choices with `setValues`, and turns off filters/sorts the API doesn't do. See Paging in ARCHITECTURE.md.
- **Dropdown filters for fixed values.** Any column whose values come from a fixed set (pick-lists, statuses, departments, yes/no, "You are") filters with a dropdown of tick boxes and counts (`filter: 'set'`; pick-list columns get it automatically from the wrapper). Columns holding a list of names (roles, tags) add `filterSplit: ','` so each name is its own choice. Free text, dates and numbers keep the typed filter, and so do columns of task names (the task tree's Task column, Sub-task of), which filter by typing part of a name.
- **Every field is editable in both the table and the form.** Anything a person may change is editable in place in its table and in the page's form or side panel; adding a field means adding it to both. Lists of names (roles, tags) are comma-separated in the table and picked in the panel; a list picked from another kind of item (the characters someone plays) uses a `pickMany` column in the table (a dropdown of tick boxes) and `TagPicker` in the form. If a row's name is editable, give the link its own Open column. Fields owned by another record stay read-only outside their home: a person's name, nickname and phone are edited on the company's People list (by admins) or the person's profile, and the sign-in email only by the person on their profile.
- **People without accounts.** A profile can exist before its person signs up (`profiles.has_account = false`); it's claimed on sign-up by email. Anything that links to a person references `profiles(id)` with `on update cascade` (and so do links to `company_members` / `project_members`). Show `InviteButtons` wherever an admin sees a person without an account.
- **Phones and emails** use `src/lib/contact.ts`: `phoneOrThrow`/`formatPhone` (stored as ###-###-####, or + and digits) and `emailOrThrow`/`emailProblem`; any new phone or email field uses them and the database's `format_phone`/`check_email`.
- **Never ask for the same information twice.** Each fact or link between items is stored once, and every page that shows it shows and changes that same record. For example, who plays a character is the character's actor: the Characters page, a shoot day's calls and the Team page all show it and can change it (helpers in `src/lib/casting.ts`). Don't add a second field for something another record already holds.

## Help pages
- **Every feature has a help page, kept current in the same PR.** Adding or changing a feature updates its page in `help/<section>/<page>.md` (see Help in ARCHITECTURE.md): plain words, the same names as the buttons on screen, numbered steps, no code or table names. Write for an iPad ("Tap"). Each fact lives on one help page; others link to it with `/help/...` links. Retake a page's screenshots (`{{shots <name>}}`) when its screen changes.

## Data and API
- The app reads and writes data only through the API client in `src/lib/api.ts`.
- API routes live in `supabase/functions/api/routes/`, with zod schemas in `schemas.ts`; run `npm run api:spec` after changing them.
- **Every table is audited.** A new table gets the `"Audit change"` trigger and a branch in `audit_row()` (see the activity log in ARCHITECTURE.md), and a new kind of item gets a History section on its form for admins (`ItemHistory`).
- Database changes are a new numbered file in `supabase/migrations` (never edit an applied one), with tests in `tests/schema.test.mjs`. Security rules live in the database (row-level security).

## Checks
`npm run typecheck`, `npm run test:db`, `npm run test:help` (every Help link and screenshot exists), `npm run build`.

## Hosting
Netlify hosts the app (`netlify.toml`): `main` publishes https://movie-prod.netlify.app/, and every pull request gets a Deploy Preview linked on the PR, built only if the checks above pass. Build in-app links from `window.location.origin` + `import.meta.env.BASE_URL` (never a hard-coded host), so they work on previews too. The footer's version is the number of the PR that was published (`appVersion` in `vite.config.ts` reads it from the merge commit), so merge PRs with GitHub's merge or squash button.
